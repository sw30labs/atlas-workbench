# ADR-015: Human decisions are versioned outside the code repository

- **Status:** accepted
- **Date:** 2026-08-05

## Context

ADR-012 gitignores runtime artifacts on the reasoning that they are
regenerated by pipeline runs, so "the recovery story is 're-run the
pipeline,' not 'restore from git.'" That holds for `atlas.db`,
`generated/`, and the scenario exports.

It does not hold for the emerging-risk register. `emerging_risks.json`
carries `review_status`, `reviewed_at`, `provenance_note`, and the
`evidence_refs` a human curated — decisions no re-run reproduces. ADR-012
swept the one unregenerable artifact in with the regenerable ones.

On 2026-08-04 a phase-2 monitoring cycle reset every re-assessed record to
`pending`, replaced each `provenance_note`, and unioned raw source-packet
URLs into `evidence_refs`. Recovering the original references was
impossible from backups: every backup on disk had been taken after the
damage, the earliest by 44 minutes. The decisions were reconstructed
instead from `review_suggestions`, which survives only because it is a
separate append-only table.

Committing the register to this repository was considered and rejected.
`docs/release/PUBLIC_RELEASE_CHECKLIST.md` gates release on the *complete git history*,
and requires that the only bundled records are the fictional CC0 fixtures
and that no `pending`, `rejected`, or `needs_update` record reaches a
released output. Governed runtime records in history would be permanent and would have
to be removed by rewriting history before release.

## Decision

Two mechanisms, neither of which puts governed runtime data in this repository.

1. **Snapshot before overwrite.** `save_emerging_risks` copies the outgoing
   file to `generated/snapshots/` before the atomic replace
   (`workbench_atlas/snapshots.py`). It is content-addressed, so an
   unchanged rewrite adds nothing, and pruned to a bounded count. A
   snapshot failure is logged and never blocks the write: refusing to save
   real work in order to protect a copy of it is the wrong trade.

2. **A separate data history.** `scripts/data_history.py` versions the data
   files in their own git directory (`~/.workbench-atlas-data.git` by
   default, `ATLAS_DATA_GIT_DIR` to override) pointed at the same working
   tree, so files stay where the application expects them. SQLite stores are
   committed as `.sql` text dumps, since the review decisions inside them are
   the point and a dump diffs where a database file does not.

ADR-012 continues to govern this repository's contents: runtime artifacts
stay gitignored here. This ADR narrows its *rationale*, which is wrong for
files holding human judgment.

## Consequences

- A destructive rewrite is recoverable without anyone having remembered to
  run anything first — the writer itself preserves the prior state.
- Diff and blame over review decisions become available, in a history that
  is never a release liability.
- Two places to look after an incident: the snapshot directory for the
  immediately-prior state, the data history for anything older.
- The data history is local. It is not a backup against disk loss; pushing
  it to a private remote is the operator's call.

## Alternatives considered

- **Track `emerging_risks.json` here** — simplest, and rejected above: the
  release gate scans complete history, so this trades a small convenience
  now for a history rewrite later.
- **Snapshot everything on every write** — the SQLite stores are large and
  genuinely regenerable; only the register earns per-write protection.
- **Rely on periodic backups** — this is what existed on 2026-08-04, and
  every copy was already too late.
